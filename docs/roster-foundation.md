# Phase 2E：1軍・2軍所属のデータ基盤

## 確定したルール

支配下／育成は選手の登録区分、1軍／2軍は現在の所属です。別の軸として扱います。

| 制約 | 上限・条件 |
|---|---|
| 球団の契約登録 | 支配下70人、育成10人 |
| 1軍登録 | 31人。支配下のみ。同一選手の重複・他球団選手・不明IDは禁止 |
| 外国人枠対象の1軍 | 合計5人、投手4人、野手4人 |
| 外国人枠免除 | `isForeign`でも`career.completedJapanSeasons >= 8`なら計算対象外（9季目から） |
| 再登録待機 | 抹消日の10日後から可。例：相対日0で抹消→9は不可、10から可 |
| 当日ベンチ | 26人、支配下かつ1軍登録済みのみ。重複・他球団・不明IDは禁止 |
| ベンチの外国人枠 | 対象4人まで。4人ちょうどなら投手・野手が少なくとも1人ずつ必要 |

上限のみを検証し、最低人数や実際に試合可能な守備編成は今回定義しません。空の登録・ベンチ一覧は上限制約上は有効です。外国人枠免除は外国人選手であること自体を変更せず、年齢やFA資格とも独立しています。

## 正式な所属状態

`GameSave.world.roster`に次を保持します。

```ts
interface RosterState {
  currentDay: GameDay;
  byTeam: Record<TeamId, { firstTeamIds: readonly PlayerId[] }>;
  deregisteredOnByPlayerId: Record<PlayerId, GameDay>;
}
```

実装の球団IDは既存の文字列IDを使います。`byTeam`には全12球団のキーが必要です。2軍ID一覧は二重保存せず、その球団に所属する選手のうち1軍ID一覧にない全選手（育成を含む）を2軍と判定します。選手本体の所属球団IDと登録区分を変更せずに、所属状態だけ更新できます。

抹消記録は選手ID単位で最新日を保持し、再登録後も残します。再度抹消した際に最新日に更新します。選手の獲得・移籍・退団処理は未実装ですが、将来は選手配列・所属一覧・抹消辞書を同じ保存単位で整合更新する必要があります。不明な選手の記録や、待機期間内に1軍へ戻った状態は保存検証で拒否します。

### 相対日の仮定

`GameDay`は非負の安全な整数で、世界開始日を0とする通算日数です。新規作成・v1/v2移行時は0で開始します。実際の日時や架空の暦年は割り当てません。保存日時のISO文字列は実時間のメタデータのままで、待機日数には使いません。

`advanceRosterDay`で明示的に進めます。後退・負数・小数・非有限値は拒否します。ページ再読み込みや実時間の経過では進みません。シーズンをまたいでも0へ戻しません。Phase 3・4では日程の通算日をこの値と同期し、その日の選手・所属・試合・統計を原子的に保存する想定です。現段階では日程進行そのものは実装していません。今後、日程側に時計を移す場合は形式移行を伴って一元化します。

## 純粋関数API

`src/game/roster/roster.ts`にUI・IndexedDB・乱数へ依存しない関数を置きます。

- `isFirstTeam(state, teamId, playerId)` / `playerSquad(state, player)`：登録・所属を判定。保存から使う前に状態を検証します。
- `countsAsForeign(player)` / `foreignCounts(players)`：日本在籍完了季数を使って枠対象を計算。
- `validateRosterState(players, unknownState)`：全12球団、ID一意性、所属・登録上限、育成、外国人枠、相対日・抹消日、待機期間内の不正登録を検証。
- `canRegisterFirstTeam(players, state, teamId, playerId)`：登録可能か判定。
- `registerFirstTeam(...)` / `deregisterFirstTeam(...)`：元配列・能力・契約を変えず、変更後の所属状態を返す。
- `advanceRosterDay(state, day)`：日程側が使う明示的な時計更新。所属検証は選手とともに`validateRosterState`で行います。
- `validateBench(players, state, teamId, ids)`：候補ID一覧を検証するだけで、自動選定・保存はしない。

判定は`{ ok: true }`または`{ ok: false, reasons: string[] }`。変更は成功時だけ`state`を返し、不正な操作で元の状態を変更しません。重複登録、育成、他球団、人数上限、外国人枠、待機期間などの理由を日本語で返します。

これらのAPIは今回UIから呼び出しません。将来の編成画面・ゲーム処理は検証済みの正式な選手状態と所属状態を入力し、成功結果を既存の世界全体と同じトランザクションで保存する構造にしてください。今回、ゲーム状態を変更する公開の保存APIや変更操作画面は追加していません。

## 初期選定の暫定設定

`src/game/roster/config.ts`で確定ルールの`rosterRules`と、暫定配分の`initialRosterConfig`を分けています。

- 投手15人（先発6人・残りは先発以外を優先）、野手16人。
- 捕手2人、その他の主守備位置も各2人。
- 同じ条件内ではIDの文字列昇順。選手配列の格納順が変わっても結果は同じ。
- 支配下から選び、育成は2軍。捕手・他7位置→先発→救援→不足する投手・野手→残候補の順で満たします。
- 毎回すべての確定ルールを優先し、不足位置や外国人上限によって配分を満たせない旧世界では、選手を追加生成せず合法な候補で補います。合法な候補が足りなければ31人未満にします。

これは戦力評価やAI采配ではなく、初期状態を作るための規則です。現在能力の合成値・OVR・潜在上限・成長タイプ・乱数・実時間を参照しません。選手生成用の乱数状態も進めません。通常の912人の世界では全12球団31人となることを複数シードで検証しています。

## 表示

既存の選手画面・検索・詳細タブを維持し、読み取り専用で次を追加します。

- 選手一覧上部に自球団の1軍登録人数と上限31人。
- 各カードに1軍／2軍のタグ（投手／野手・支配下／育成タグと併記）。
- 詳細上部に現在所属。

`toPublicPlayer(player, roster)`は検証済みの所属状態を入力し、公開DTOに` squad: "first" | "farm" `を明示的に追加します。成長タイプ、潜在上限、世界全体、抹消辞書はReactへ渡しません。外国人枠の内部判定に使う日本完了季数も今回の表示DTOには追加しません。選手の検索・詳細閲覧は保存値を変更しません。

## 手動確認

1. `npm run dev`で起動し、新規ゲームを開始するか既存スロットを読み込みます。
2. 「選手」で自球団の1軍31人、各カードの1軍／2軍と支配下／育成を確認します。育成はすべて2軍です。
3. 表示球団を切り替え、全12球団の所属表示を確認します。検索・能力順比較も従来どおり利用できます。
4. 1軍と2軍の選手をそれぞれ開き、詳細上部の現在所属と4タブを確認します。
5. 手動保存・再読み込み・別スロット切り替え後も、その世界の所属が維持されることを確認します。
6. 旧v2スロットなら読込時にv3へ移行し、選手・能力・成績・日時は維持されます。不正・未対応スロットはエラーを表示し保護します。

登録変更・日付進行・ベンチ選定のUIはありません。再登録待機やベンチの境界は純粋関数の自動テストで検証します。
