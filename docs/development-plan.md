# 架空プロ野球ペナントゲーム 開発実行計画 v1.0

- 基準文書：`docs/requirements.md`（質問1〜148の確定仕様）
- 状態：**実装方針の提案**。採択済みゲーム仕様の変更ではない。
- 目的：スマートフォン縦画面で動く、オフライン対応の個人用ブラウザゲームを段階的に完成させる。

## 1. 推奨技術構成（提案）

| 項目 | 推奨 | 理由 |
|---|---|---|
| UI | React + TypeScript + Vite | スマホUIの画面分割、型安全、軽量な初期構築 |
| スタイリング | CSS（まずは標準CSS） | 複雑なデザインライブラリを初期依存にしない |
| ゲームロジック | TypeScriptの純粋関数中心 | UIとは独立に試合計算をテストできる |
| 乱数 | 保存可能なシード付きPRNG | セーブ/復旧・再現性のあるデバッグ |
| 保存 | IndexedDB（小規模ラッパーを使用） | 複数スロット・日単位の整合保存 |
| テスト | Vitest、必要ならPlaywright | 試合/規則の自動テストとスマホ操作の検証 |
| 配信 | Cloudflare Pagesなど静的ホスティング | 初回取得後オフライン動作、サーバー運営不要 |
| オフライン | Service Worker | 通信不能時の画面・アセット利用 |

**注意：** フレームワークやライブラリの選択はゲーム内仕様ではなく、開発開始時の技術提案。パッケージ版数は作成時点で互換性を確認する。

## 2. 開発上の原則

1. 採択済みの148件と矛盾する機能を独断で追加しない。特に総合能力値、特殊能力、捕手リード、選手画像、球団ロゴ、選手編集を作らない。
2. 各段階は独立してブラウザ起動とテストを通せる状態にし、小さな単位で変更・レビューする。
3. UIとシミュレーションを分離する。成績計算の正当性を見た目より優先する。
4. 日単位の更新は、試合・統計・成長・資金等を一貫して処理し、完了時にのみ保存する。途中状態を永続化しない。
5. セーブ形式にバージョンを付け、更新前データの取り込み・移行テストを用意する。
6. 乱数のシードを保持し、テスト時に同じ条件で同じ結果を再現できるようにする。実際のゲームでは新規セーブごとに異なるシードで選手を生成する。
7. 実装時の仮定や係数は設定ファイルに集約し、ユーザー採択済みのルールと区別する。

## 3. 開発フェーズと合格条件

### Phase 0: リポジトリと実装ルール
- GitHubの専用非公開リポジトリを準備。
- 要件定義書、開発計画、Codex作業ガイドを追加。
- コードは `main` に直接大量追加せず、機能単位のコミット／Pull Requestで管理。
- **完了条件**：GitHub上で3文書が閲覧でき、Codexからリポジトリを選択できる。

### Phase 1: 動作する最小のゲーム画面
- TypeScript + React + Vite 初期構築。
- スマートフォン縦画面、下部5カテゴリの固定ナビ。
- ブルー/レッド各6球団と球団カラー、球団選択画面。
- 新規セーブのスロット作成、IndexedDBへの保存と読み込み。
- **完了条件**：スマホ/PCから起動でき、12球団を選び、再読み込み後も自球団が復元できる。
- **意図的に未実装**：試合、選手自動生成、ドラフト、FAなど。

### Phase 2: 選手・チームのデータモデル
- 支配下最大70・育成最大10、1軍登録最大31の型と制約。
- 架空選手の新規生成。投打・守備・身体能力・現実績、隠し成長パラメーター、初期単年契約。
- 選手詳細タブ、全12球団の選手閲覧と検索。
- **完了条件**：生成選手を閲覧でき、制限違反を許さず、セーブ後の値が保持される。

### Phase 3: 1試合の打席単位シミュレーション
- 9回〜延長12回、DH、打席結果、進塁、失策、投球疲労、AI采配。
- 右/左投手用の打順、先発/救援/ベンチ役割。
- スコア、個人成績、テキスト試合ログ。
- テスト：総得点と個人打点等の整合、アウト・塁・守備交代、引分け処理など。
- **完了条件**：固定シードの試合が再現可能で、スコア集計・球数・野球規則に矛盾がない。

### Phase 4: 1シーズンの自動進行
- 143試合の1軍日程（同リーグ125＋交流18）、独立した2軍日程100〜120試合。
- 日・週・月の進行、重要判断での停止、中断ボタン、期間サマリー。
- 日ごとの整合的な自動保存・復元、3シーズン詳細履歴。
- **完了条件**：12球団すべてが予定試合数を正しく消化し、順位と全成績が整合する。

### Phase 5: 育成・編成・契約・オフシーズン
- 体力・調子・故障、月次成長、コーチ、2軍重点育成。
- 1軍31/ベンチ26、抹消10日、外国人枠、支配下登録期限。
- ドラフト、外国人調査、FA、トレード、契約更改、複数年契約、予算。
- 契約更改の進行不能を防ぐ仕組みを、既決仕様に反しない形で設計・テスト。
- **完了条件**：2月キャンプから翌年2月まで問題なく進み、予算・登録の制限違反がない。

### Phase 6: 長期運営と完成度向上
- CS・日本シリーズ・オールスター、個人タイトル、表彰、殿堂入り。
- FA再取得・外国人枠免除、選手引退と歴代記録。
- JSONエクスポート/インポート、保存形式移行、Service Workerオフライン対応。
- スマホ操作と長期（例：10〜20年）進行の負荷テスト。
- **完了条件**：オフラインで複数年プレイでき、バックアップからの復元、制約検証が通る。

## 4. 初回にCodexへ頼む作業（Phase 1用プロンプトのたたき台）

> まず docs/requirements.md を読み、確定仕様を変更せず、React・TypeScript・Vite の最小プロジェクトを構築してください。スマートフォン縦画面を優先し、下部固定メニューに「ホーム・選手・日程・データ・球団運営」を配置してください。ブルーリーグ6球団、レッドリーグ6球団の確定名称を表示し、球団選択後は IndexedDB の現在の共通スロットへ保存して、再読み込み後も選択が復元されるようにしてください。架空球団は名称とチームカラーだけで表示し、ロゴ・顔画像・ユニフォームを追加しないでください。試合シミュレーションなど未着手の機能は「準備中」と明示し、ダミー成績を実データと誤認させないでください。型チェックと最低限のテストを追加し、変更点と実行方法を説明してください。

**適用時の注意：** まずPhase 0で資料とCodex作業ガイドをリポジトリへ追加し、リポジトリへのアクセス確認を済ませる。

## 5. リスク・未確定事項（仕様の変更ではない）

- 野球らしい試合統計を維持する係数・分布は、試験データを多数生成して調整する必要がある。
- 同一リーグ125試合の対戦配分など日程制約を機械的に検証する必要がある。
- 「契約解除でも残年俸債務が残る」「赤字禁止」「更改未完了で先へ進めない」の組合せはデッドロック対策が必要。ユーザーの承認なしの自動解雇はしない。
- 日付の整合保存、データ容量、オフライン更新、モバイル環境でのIndexedDB消去リスクをテストし、JSONバックアップを定期的に案内する。
- 個人用利用を前提にした設計であり、マルチユーザー対応やクラウド同期は追加しない。
