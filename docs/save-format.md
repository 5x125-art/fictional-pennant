# セーブ形式と移行（Phase 2E / v3）

## 論理形式

`GameSave`は`schemaVersion: 3`です。

| 項目 | 内容 |
|---|---|
| `id` | セーブスロットID。旧形式からも維持 |
| `teamId` | 操作球団ID。確定後は変更不可 |
| `createdAt` / `updatedAt` | ISO日時。移行・読み込みだけでは変更しない |
| `world.players` | 12球団の保存済み選手。初期912人（各76人） |
| `world.developmentByPlayerId` | 選手ID別の非公開成長タイプ・能力別上限 |
| `world.seed` / `generationVersion` | 初期生成シード・生成実装バージョン |
| `world.roster` | 全12球団の1軍ID一覧、相対日、選手別の最終抹消日。2軍は差集合 |
| `world.randomState` | 後続シミュレーション用のシード付き乱数状態 |

`world`は選択前の`phase`を除いた正式なゲーム状態です。シードは初期生成の由来として保持し、読み込み時に再生成するためには使いません。将来の移籍・引退・入団・成長はこの保存済み状態を更新する設計です。読み込み検証も人数を初期912人に固定せず、ID・所属・登録上限・能力・契約・経歴・成績・非公開情報との対応などを検証します。試合・育成・移籍そのものの処理は今回追加していません。

## IndexedDBの物理形式

DB名は従来と同じ`fictional-pennant`、DBバージョンは2です。DBバージョンと各レコードの`schemaVersion`は別の概念です。

| ストア | キー | 値 |
|---|---|---|
| `saves` | `id` | ID・操作球団・日時・schemaVersion。v2/v3は`initialSeed`も保持 |
| `worlds` | `id` | `{ id, world }`：当該スロットの選手・非公開情報・乱数状態 |
| `settings` | `activeId` | 最後に読み込んだスロットID |
| `drafts` | `pending` | `{ key, id, selectedTeamId, world }`：球団選択前の世界 |

従来のDBバージョン1→2のアップグレードでは`worlds`・`drafts`を追加するだけで、従来の`saves`・`settings`は削除・初期化しません。

一覧用`readSaves()`は`saves`・`settings`だけを読みます。全スロット分の選手や成長情報を読み出したり、一覧表示だけで旧データを一括移行したりしません。v1・v2・v3は同じ一覧に表示されます。未対応・破損したメタデータは変更せず、警告を返し、正常なスロットの一覧表示を続けます。

ゲーム処理用の`readGameSave(id)`は移行済みv3メタデータと本体を読み、シードとスロットIDの対応も検証します。UIはこの本体APIを利用しません。

## v1/v2からv3への移行

一覧表示では旧レコードを変更しません。`loadSave(id)`で選んだスロット（起動時のアクティブ復元を含む）、または`saveCurrent(id)`で明示的に保存するスロットだけが対象です。`readGameSave`や公開DTOの読取APIは移行・書込を行わず、未移行なら読込操作を案内します。

- v2：検証済みの保存済み選手世界に、決定的な`createInitialRosters(players)`の所属状態を追加し、schemaVersionを3にします。選手の再生成・乱数呼出し・乱数状態更新は行いません。
- v1：旧スロットIDから固定FNV-1a（UTF-16コード単位）でシードを得て生成バージョン1の世界を一度だけ生成します。その世界へ同じ所属初期化を行い、直接v3で保存します。途中のv2を別トランザクションで保存しません。

移行ではID、操作球団、作成日時、更新日時をそのまま維持します。v2の全選手ID・名前・年齢・現在能力・成績・契約・経歴・非公開成長情報・生成シード・生成バージョン・乱数状態を変更しません。所属初期化は乱数や潜在情報を使わず、入力配列の順序にも依存しません。配分と相対日0の仮定は[所属モデル](roster-foundation.md)を参照してください。

同じIndexedDB readwriteトランザクション内で、本体（v1はadd、v2はput）・v3メタデータ・アクティブ選択を更新します。成功はtx.oncomplete後だけ返します。途中の同期例外、要求エラー、容量不足、最後の要求成功後のabortでも、メタデータ・本体・アクティブ選択をまとめてロールバックし、旧データを維持します。

移行後はv3として保存された所属を検証して読み、初期選定を呼びません。登録人数が初期31人と違っていても合法ならその状態を維持します。所属欠落・不明ID・重複・他球団・育成・外国人超過・不正な相対日・抹消記録は破損として拒否し、勝手な再選定や修復はしません。未対応スキーマも初期化しません。

手動保存は正式状態を読み検証してメタデータの更新日時だけを変えます。選手・所属・抹消日・相対日・シード・乱数状態は変えません。現在の新規ゲーム準備データは従来どおり保持し、球団選択確定時に所属を追加したv3を作成します。IndexedDB自体のバージョンは2のままです。

## 球団選択前の世界

- 初回の新規ゲーム画面で全12球団を生成し、準備データをIndexedDBへ保存します。保存完了後に選択・確認操作を有効にします。
- 初期シードは`crypto.getRandomValues()`で取得し、既存スロットのシード（未移行v1の決定済みシードも含む）と衝突した場合は空いているuint32値へ進めます。
- IDは既存の安全なUUID生成（`randomUUID`優先、利用できないHTTP環境では`getRandomValues`）を使います。
- 名前・年齢・投打・主守備位置・登録区分・現在能力の一部を、全12球団から簡易プレビューできます。0〜100系能力は数値とS〜Gランクを併記し、球速はkm/hで表示します。保存済みデータの詳細閲覧はPhase 2Cで実装しました。検索・絞り込みはPhase 2Dで実装済みです。
- 表示球団の切り替えは表示だけを変えます。操作球団の候補変更は同じ準備データの`selectedTeamId`だけを更新します。
- 再読み込み後も準備世界・操作球団候補を復元します。プレビューの表示球団は先頭球団へ戻ります。
- 「キャンセル」は画面を戻す操作で、準備世界を捨てません。もう一度新規スロットを始めても同じ準備世界を再開するため、リロールできません。
- 確定時はスロット追加・本体保存・現在スロット選択・準備データ削除を同一トランザクションで行います。失敗時は準備世界を残します。
- 確定後の次の新規スロットには別のシード・別の世界を生成します。

同じオリジンの複数タブでは準備データを1件共有します。同時生成はトランザクションで直列化し、既存の準備世界を再利用します。別のタブで選択が変わったり確定されたりした場合、古いID・球団での確定はエラーにして上書きを防ぎます。

## 非公開情報とエラー

保存本体には成長情報が必要ですが、表示用`DraftView`・`PlayerPreview`には明示的なホワイトリストで取り出した公開情報しか含めません。世界全体や成長辞書をUIへ丸ごと渡しません。Phase 2Cの選手画面では別の公開DTOを使い、保存済みの経歴と成績もホワイトリストでコピーします。名前・現在能力以外の成長タイプ・潜在上限はプレビューにも出しません。潜在情報を暗号化する仕組みではなく、表示境界の分離です。

容量不足、制約違反、検証・生成の失敗ではトランザクションを中断します。旧メタデータを残し、半端な本体やスロットを追加せず、現在スロットも切り替えません。未対応スキーマ・破損した本体・準備データに対して、黙って初期化・修復・再生成する処理はありません。エラー時は成功メッセージを表示しません。

## 破損・未対応スロットがある場合の起動

一覧の警告と、前回アクティブだったスロットの復元失敗は、ほかのスロットや新規ゲーム準備から分離して扱います。読み込めた正常スロットだけをプレイ中とし、復元できない場合も一覧を残して、新しいIDの準備世界を作成できます。新規操作が可能になっても問題のあるスロットを初期化・再生成・削除・上書きしません。

警告は球団候補の変更、新規作成、正常スロットの読み込み中も画面に保持します（再読み込みで改めて検証します）。アクティブスロットがない場合にも、新しいスロットを始めるボタンを使えます。準備操作自体が失敗した場合も、そのボタンで再試行できます。破損した準備データを黙って作り直すことはありません。

回帰テストでは、破損した旧セーブのみ、未対応形式と正常スロットの混在、アクティブ本体の破損、アクティブ旧セーブの破損、および正常アクティブと未対応データの混在を検証します。問題のあるメタデータ・本体が操作前後で完全一致することを確認します。

Phase 2Eの検証結果と追加した所属・移行テストは[所属基盤](roster-foundation.md)を参照してください。

自動検証では912人／球団ごとの76人、全選手と成長情報の復元、手動保存での不変性、スロット間分離、旧形式と新形式の混在・遅延移行、日時保持、容量不足・非同期制約違反時のロールバック、破損検出、選択前リロール防止、公開DTO、一覧読み込みのストア範囲を確認します。PCとスマートフォンのブラウザでは通常操作に加え、旧DBからの起動・移行、プレビュー切替と再読み込み、移行・新規保存の容量不足表示と再試行も確認します。

手動では`npm run dev`で起動し、球団選択前に「球団選択前に選手を確認」を開いて表示球団を切り替えます。操作球団候補を変更して再読み込みし、同じ選手と候補が復元されることを確認します。確定後に手動保存・再読み込み・新規スロット作成・元スロット読み込みを確認してください。既存v1スロットがある場合は読み込みを行い、操作球団と保存日時が維持されることを確認できます。
