# Phase 2B：セーブ形式と移行

## 論理形式

`GameSave`は`schemaVersion: 2`です。

| 項目 | 内容 |
|---|---|
| `id` | セーブスロットID。旧形式からも維持 |
| `teamId` | 操作球団ID。確定後は変更不可 |
| `createdAt` / `updatedAt` | ISO日時。移行・読み込みだけでは変更しない |
| `world.players` | 12球団の保存済み選手。初期912人（各76人） |
| `world.developmentByPlayerId` | 選手ID別の非公開成長タイプ・能力別上限 |
| `world.seed` / `generationVersion` | 初期生成シード・生成実装バージョン |
| `world.randomState` | 後続シミュレーション用のシード付き乱数状態 |

`world`は選択前の`phase`を除いた正式なゲーム状態です。シードは初期生成の由来として保持し、読み込み時に再生成するためには使いません。将来の移籍・引退・入団・成長はこの保存済み状態を更新する設計です。読み込み検証も人数を初期912人に固定せず、ID・所属・登録上限・能力・契約・経歴・成績・非公開情報との対応などを検証します。試合・育成・移籍そのものの処理は今回追加していません。

## IndexedDBの物理形式

DB名は従来と同じ`fictional-pennant`、DBバージョンは2です。DBバージョンと各レコードの`schemaVersion`は別の概念です。

| ストア | キー | 値 |
|---|---|---|
| `saves` | `id` | ID・操作球団・日時・schemaVersion。v2のみ`initialSeed`も保持 |
| `worlds` | `id` | `{ id, world }`：当該スロットの選手・非公開情報・乱数状態 |
| `settings` | `activeId` | 最後に読み込んだスロットID |
| `drafts` | `pending` | `{ key, id, selectedTeamId, world }`：球団選択前の世界 |

DBのアップグレードでは`worlds`・`drafts`を追加するだけで、従来の`saves`・`settings`は削除・初期化しません。

一覧用`readSaves()`は`saves`・`settings`だけを読みます。全スロット分の選手や成長情報を読み出したり、一覧表示だけで旧データを一括移行したりしません。v1・v2は同じ一覧に表示されます。未対応・破損したメタデータは変更せず、警告を返し、正常なスロットの一覧表示を続けます。

ゲーム処理用の`readGameSave(id)`はv2メタデータと本体を読み、シードとスロットIDの対応も検証します。UIはこの本体APIを利用しません。

## 旧形式からの移行

1. 一覧表示ではschemaVersion 1をそのまま残します。
2. `loadSave(id)`で選択された旧スロットだけを移行します。起動時は最後に選択していたスロットを読み込むため、その旧スロットが対象になります。
3. スロットIDのUTF-16コード単位に固定のFNV-1aを適用してuint32シードを得ます。乱数や日時をシードの入力にしません。同じIDなら失敗後の再試行でも同じ初期世界になります。
4. Phase 2Aの生成バージョン1で世界を一度生成します。
5. 同じreadwriteトランザクションで本体追加・v2メタデータ更新・現在スロット選択を実施します。完了イベントが来たときだけ成功とします。
6. ID・操作球団・作成日時・更新日時は旧レコードの値をそのまま維持します。

移行後は保存した本体を読み、再生成しません。手動保存では正式状態を読み込んで検証し、メタデータの更新日時だけを更新します。操作球団・作成日時・選手・成長情報・シード・乱数状態は変えません。

## 球団選択前の世界

- 初回の新規ゲーム画面で全12球団を生成し、準備データをIndexedDBへ保存します。保存完了後に選択・確認操作を有効にします。
- 初期シードは`crypto.getRandomValues()`で取得し、既存スロットのシード（未移行v1の決定済みシードも含む）と衝突した場合は空いているuint32値へ進めます。
- IDは既存の安全なUUID生成（`randomUUID`優先、利用できないHTTP環境では`getRandomValues`）を使います。
- 名前・年齢・投打・主守備位置・登録区分・現在能力の一部を、全12球団から簡易プレビューできます。0〜100系能力は数値とS〜Gランクを併記し、球速はkm/hで表示します。詳細・検索・絞り込みはPhase 2Cの対象です。
- 表示球団の切り替えは表示だけを変えます。操作球団の候補変更は同じ準備データの`selectedTeamId`だけを更新します。
- 再読み込み後も準備世界・操作球団候補を復元します。プレビューの表示球団は先頭球団へ戻ります。
- 「キャンセル」は画面を戻す操作で、準備世界を捨てません。もう一度新規スロットを始めても同じ準備世界を再開するため、リロールできません。
- 確定時はスロット追加・本体保存・現在スロット選択・準備データ削除を同一トランザクションで行います。失敗時は準備世界を残します。
- 確定後の次の新規スロットには別のシード・別の世界を生成します。

同じオリジンの複数タブでは準備データを1件共有します。同時生成はトランザクションで直列化し、既存の準備世界を再利用します。別のタブで選択が変わったり確定されたりした場合、古いID・球団での確定はエラーにして上書きを防ぎます。

## 非公開情報とエラー

保存本体には成長情報が必要ですが、表示用`DraftView`・`PlayerPreview`には明示的なホワイトリストで取り出した公開情報しか含めません。世界全体や成長辞書、経歴をUIへ丸ごと渡しません。名前・現在能力以外の成長タイプ・潜在上限はプレビューにも出しません。潜在情報を暗号化する仕組みではなく、表示境界の分離です。

容量不足、制約違反、検証・生成の失敗ではトランザクションを中断します。旧メタデータを残し、半端な本体やスロットを追加せず、現在スロットも切り替えません。未対応スキーマ・破損した本体・準備データに対して、黙って初期化・修復・再生成する処理はありません。エラー時は成功メッセージを表示しません。

## 破損・未対応スロットがある場合の起動

一覧の警告と、前回アクティブだったスロットの復元失敗は、ほかのスロットや新規ゲーム準備から分離して扱います。読み込めた正常スロットだけをプレイ中とし、復元できない場合も一覧を残して、新しいIDの準備世界を作成できます。新規操作が可能になっても問題のあるスロットを初期化・再生成・削除・上書きしません。

警告は球団候補の変更、新規作成、正常スロットの読み込み中も画面に保持します（再読み込みで改めて検証します）。アクティブスロットがない場合にも、新しいスロットを始めるボタンを使えます。準備操作自体が失敗した場合も、そのボタンで再試行できます。破損した準備データを黙って作り直すことはありません。

回帰テストでは、破損した旧セーブのみ、未対応形式と正常スロットの混在、アクティブ本体の破損、アクティブ旧セーブの破損、および正常アクティブと未対応データの混在を検証します。問題のあるメタデータ・本体が操作前後で完全一致することを確認します。
